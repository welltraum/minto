**Audit of the “Period Graph Books” memo against the Minto Pyramid Principle**

| Minto Principle Element | Defect(s) Identified | What Must Change |
|--------------------------|----------------------|------------------|
| **1. Top‑Down Structure** – Start with the *answer* (key recommendation) followed by supporting arguments. | • The memo opens with a neutral “Subject” line and a narrative description of the situation; the *decision* or *recommendation* is missing. <br>• The “Overall assessment” is a vague summary rather than a clear, actionable conclusion. | • Begin with a concise statement of the recommended action (e.g., “Consolidate the graph‑book production process into a single, controlled workflow to eliminate duplication and errors”). <br>• Follow with the three‑point supporting argument (e.g., “(1) Current process is fragmented; (2) Errors stem from multiple data re‑entries; (3) The team lacks capacity to implement needed changes”). |
| **2. Logical Flow (SCQA)** – Situation, Complication, Question, Answer. | • Situation is described, but the *complication* (errors) is interwoven with process steps, making the problem hard to isolate. <br>• No explicit *question* that the memo is asking the reader to answer. <br>• The *answer* (recommendation) is absent. | • Separate the Situation (current ownership and process), the Complication (specific errors and inefficiencies), the Question (e.g., “How should we restructure the production of the graph books?”), and the Answer (the recommended restructuring). |
| **3. MECE Grouping** – Mutually exclusive, collectively exhaustive. | • “Production” steps and “Issues” are not mutually exclusive; some issues (e.g., “inconsistent data”) are repeated across steps. <br>• The list of issues mixes symptoms (inconsistent data) with root causes (multiple re‑entries) without clear categorisation. | • Re‑group content into distinct, non‑overlapping categories (e.g., **Process Inefficiencies**, **Data Integrity Problems**, **Responsibility Gaps**). <br>• Ensure every problem is captured once and all relevant problems are covered. |
| **4. Hierarchical Headings** – Each level should answer “why?” for the level above. | • Only one heading (“Subject: Period Graph Books”) is used; sub‑headings (“Production”, “Issues”, “Overall assessment”) are flat and do not reflect a hierarchy of arguments. | • Introduce a top‑level heading that states the recommendation. <br>• Use second‑level headings for the three supporting arguments. <br>• Use third‑level headings for evidence (process steps, error examples). |
| **5. Pyramid Shape of Paragraphs** – Each paragraph should start with its main point. | • Paragraphs begin with narrative (“Since Period 5…”) and then drift into details, making the main point hard to locate. | • Rewrite each paragraph (without actually rewriting the text) so the first sentence states the key point (e.g., “The current workflow requires three separate data entries, which creates duplication and error risk.”) followed by supporting details. |
| **6. Clarity & Brevity** – Avoid unnecessary detail before the point is made. | • The “Production” section lists low‑level tasks before explaining why they matter. <br>• The memo includes filler (“telephone calls”) that does not add to the argument. | • Move detailed step‑by‑step descriptions to an appendix or a supporting “Evidence” section. <br>• Keep the main body focused on the logical argument. |
| **7. Actionability** – Reader should know exactly what to do next. | • The closing sentence (“Could we discuss how best to proceed?”) is vague and does not specify the next step. | • End with a concrete call‑to‑action (e.g., “Approve the formation of a cross‑functional task force to redesign the graph‑book workflow by [date]”). |
| **8. Consistency of Terminology** | • Terms such as “Color Graphics,” “Corporate computer,” “dedicated corporate program” are introduced without definition, causing potential confusion. | • Standardise terminology and define each entity once; use the same term throughout the memo. |
| **9. Audience‑Focused Framing** | • The memo assumes the reader knows the history of the transfer; no explicit statement of why senior management should care. | • Open with a brief statement of impact on senior management (e.g., “These errors delay quarterly presentations and risk inaccurate financial reporting to the Board”). |
| **10. Use of Data / Evidence** | • No quantitative evidence (e.g., number of errors, time lost) is provided to substantiate the severity of the problem. | • Include concise data points or metrics in the supporting evidence section to make the case compelling. |

**Summary of Required Changes**

1. **Insert a clear, top‑level recommendation** (the “Answer”) at the start of the memo.  
2. **Re‑structure using SCQA**: Situation → Complication → Question → Answer.  
3. **Group issues into MECE categories** and ensure each point appears only once.  
4. **Introduce hierarchical headings** that reflect the logical pyramid (Recommendation → Supporting Arguments → Evidence).  
5. **Rewrite paragraph openings** to state the main point first, then provide details.  
6. **Trim extraneous process detail** from the main body; move it to an appendix or evidence section.  
7. **End with a specific, actionable next step** for senior management.  
8. **Standardise terminology** and define any specialized terms.  
9. **Add a brief impact statement** to orient the audience to why the issue matters.  
10. **Insert quantitative evidence** (error counts, time/cost impact) to strengthen the argument.
